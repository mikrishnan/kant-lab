How to Contribute

Kant Lab

You don't need to install anything or read code. You need a browser, a GitHub account, and an idea. Every tool on the site travels the same road:

→ →

Step 1 · Try an idea in your own folder

Individuals/your-name/ is your sandbox. Nobody reviews it, and nothing you do there can break anyone else's work.

  1. Open claude.ai/code and pick the mikrishnan/kant-lab repository.
  2. Paste the request below. Claude builds the page and replies with a preview link.
  3. Open the link, look, and ask for the next change. Repeat.
  4. When you like it, say “Open a pull request.” On GitHub, press Squash and merge no approval needed.

Without Claude

On github.com, open Individuals/, press Add file → Upload files (or open a file and click the pencil), and choose Create a new branch for this commit and start a pull request. Then press Squash and merge on the pull request's page. Name new folders and files with hyphens, not spaces, so links survive being pasted into an email.

Step 2 · Build it together in a working group

When an idea deserves more hands, a few of you form a group. The group gets a folder, groups/group-name/, and its tool appears on the site under Works in progress.

  1. Find at least one partner, so that you can review each other's work.
  2. File a New working group issue. The professor creates your folder.
  3. Together, write SPEC.md: what question the tool answers, and a numbered list of things it does that anyone can check by clicking.
  4. One person asks Claude to build one spec item at a time, and opens a pull request.
  5. Another member checks it with the preview link and approves it another group member approves.

If you already built a version in Individuals/, put its path in the issue's Starting from field. Once the group's folder exists, its first pull request copies your page in and drafts the spec from what the page does:

Your original stays where it was, yours to keep. Whoever reviews this pull request checks each drafted spec item against the page, so it is the spec's first review too.

What a spec looks like

Question · the scholarly question the tool helps with.
Sources · which texts, and which files in data/.
Attested vs. inferred · what the tool works out for itself, and how it shows that.
Behaviour · numbered statements, each true or false of the page, e.g. “4. Clicking a § number scrolls the text to that §.”
Out of scope · what it deliberately doesn't do.

The spec is the part you own and argue about. Claude writes the code; the spec is how you tell it what to build, and how your teammates check that it did.

Step 3 · Make it a tool

When your group thinks the tool is polished and does everything its spec says, file a Proposal issue asking for it to be promoted. With the professor's approval it moves to the top of the site, beside the Baumgarten Reader, the Meier Reader and the Porphyrian Tree professor approves.

The exact steps are still being worked out. Two things are settled: links people have already shared keep working, and from then on improvements to the tool arrive as pull requests the professor reviews, like those to the other tools.

Other ways to help

Not every contribution is a new tool. Most of these take ten minutes.

  • Report a text error

    A wrong word, §, Reflexion or citation in any tool. You are the experts on the texts, and these reports are among the most valuable things anyone files. Give the AA reference. Text error form →

  • Report a bug, or propose a feature

    Something doesn't work, or you wish a tool did something. Say what you did and what you expected. Bug form → · Proposal form →

  • Join the conversation

    Comment on other people's issues, and help a group argue out its spec. Ideas get better when someone else pushes on them.

  • Review a pull request

    You review by using, not by reading code: open the pull request's preview link, check each spec item it claims, and look at the browser console (Ctrl+Shift+J, or ⌥⌘J on a Mac) for red errors. Then approve, or comment saying which item failed.

  • Provide translations

    Much of what the tools show is untranslated: Baumgarten's Latin, Meier's German, Adickes' notes like the one in Step 1. A translation is a new layer beside the original, never a replacement for it, and it says who translated it, since it is not what the AA prints. Start with a Proposal saying which text, then build it as a dataset in your own folder or a group's, keyed to the §, Reflexion or phase it translates.

  • Add a parallel passage to the Meier Reader

    The reader's Tradition panel sets passages from Wolff, the Scholastics and Aristotle beside Meier's §§, and only 10 of his 563 §§ have any yet. They live in data/tradition-meier.js, whose first lines explain how to add one; no code involved professor approves.

  • Build a dataset

    Tools are only as good as their data. The Jäsche Logik, Kant's own lectures on Meier's Auszug, is already transcribed in the repository and nothing uses it yet. A group can turn it into data other tools read.

House rules

  • Stay in your folder. A change that reaches outside it needs the professor.
  • Include shared data; never copy it. A copy goes stale.
  • Attested vs. inferred. Show what the AA says as it says it, query marks and all, and visibly mark anything the tool works out for itself.
  • No readings, books or PDFs. The repository and the site are public.
  • One driver per tool at a time. Two people changing one file at once is how conflicts happen.
  • If a pull request has conflicts, close it and ask for the same change again. Redoing is quicker than untangling.
  • If a merged change breaks something, press Revert on its pull request first, and ask questions afterwards.

Words you'll meet
Repository
The project's files on GitHub, with every change ever made to them.
Issue
A numbered discussion thread: an idea, a bug, a question.
Branch
A private copy of the files where a change is made, so the live site isn't touched until it's ready.
Pull request
A request to bring a branch's changes into the live site, with a place to discuss and approve them.
Preview link
A raw.githack.com address showing a page as it stands on a branch, before it's merged.
Squash and merge
The button that accepts a pull request. The site updates a few minutes later.
Spec
A group's SPEC.md: what its tool is for, and what it does, item by item.
